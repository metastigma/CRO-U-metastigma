# Сюжетное поражение: первый бой Omega (группа 650)

**Дата:** 2026-11-06  
**Ветка:** `fix/scripted-battle-loss-resumes-event`  
**Статус:** узкое исправление и регрессионный self-test внесены в эту ветку; CI и запуск на реальных игровых данных ещё не подтверждены.

## Цель

Первый сюжетный бой должен завершиться поражением героя и продолжением сюжетного сценария. Реконструкция вместо этого выводит игрока на титульный экран. Поведение нужно переносить из оригинального кода Omega, а не выводить из названий ресурсов или из текущего поведения порта.

## Источники и границы доказательств

| Источник | Что подтверждает | Статус |
|---|---|---|
| Оригинальный iOS `ChaosRingsOmegaHDeng`, Mach-O ARMv7 из пользовательского `ChaosRingsOmega.zip` | Нативный обработчик EVT `Battle`, обработка группы 650 и установка сюжетного gate-флага | Код незашифрован: `cryptid=0`; основной источник анализа |
| `j001_t01.evt` из того же архива | Сценарий 202 вызывает `Battle(650, 0)`, затем `Gosub 0xA1BF` | Проверено по оригинальному EVT |
| `eboot.bin` из того же архива | Это Vita SELF | Сегменты помечены зашифрованными; Vita-код пока не подтверждён дизассемблированием |
| `CRO-U-metastigma/engine/src/main.cpp` | Текущий переход порта после `Battle::Lost` | Проверено по исходнику ветки `main` |

**Ограничение:** совпадение поведения iOS и Vita пока не заявляется. Наличие Vita `eboot.bin` само по себе не доказывает, что Vita использует тот же путь.

## Оригинальная сценарная последовательность

В `j001_t01.evt`, событие **202**:

| Смещение в EVT | Команда | Значение |
|---:|---|---|
| `0xA124` | `Battle` | группа `650` (`0x28A`), stage `0`, flags `0` |
| `0xA129` | `Gosub` | продолжение по адресу `0xA1BF` |

После возврата из боя скрипт не должен заменяться новым комнатным entry-скриптом или титульным экраном: исполняться должна следующая команда уже приостановленного EVT. В `Gosub 0xA1BF` находится сцена с Вигом, Олгаром и Агентом; среди реплик — «Олгар?!», «Думал, я позволю тебе сделать это в одиночку?» и «Дураки. Вы — двое».

## Оригинальная iOS-реализация

1. Нативный обработчик EVT `Battle` находится по адресу **`0x22C8C`**. Он читает из байткода группу, stage и flags, помещает параметры в глобальный контекст боя и запрашивает переход в боевой режим.
2. В нативной процедуре обработки завершения боя **`0x64D5C`** обнаружена отдельная проверка группы **`0x28A` (650)**.
3. Связанная ветка в **`0x64E80`** устанавливает флаг события **`0xFFF`** через функцию установки флага **`0x20340`**. Это специальный сюжетный переход для группы 650; его нельзя заменять общей реакцией на поражение.
4. В этой же системе `0xFFF` используется как gate для исполнения событийного скрипта во время боя. Не следует называть его отдельным «флагом спасения Пиу-Пиу»: доказано его участие в управлении сюжетным EVT, а не полная семантика всех последующих проверок.

**Важно:** сейчас задокументирован нативный специальный путь группы 650 и сценарное продолжение. Точная ветка оплаты Пиу-Пиу, порог Oz и все исходы при недостатке денег требуют отдельной трассировки оригинальных проверок; они не должны подменяться догадкой.

## Что должно происходить на экране при поражении

**Сообщение и поза поверженной пары — часть оригинального поражения, их удалять нельзя.**

- В оригинальном `sys.evt`, системное сообщение **57016** имеет языковые варианты. В слоте 0 японский текст — `{STR:0}は戦いに敗れた・・・`; в слоте 1, который в используемой локализации содержит русский текст, точная строка — **`{STR:0} и команда повержены...`**. Во французском и немецком слотах тоже прямо сказано, что команда повержена. Значит, сообщение, которое появилось в твоём запуске, — оригинальное штатное сообщение, не лишняя реплика порта.
- В текущем runtime-пути порта для результата `Lost` (вызов из `endRound()`) уже воспроизводятся отдельная музыка поражения `0x1A`, голосовой набор проигрыша для пары, камера `0x48`, скрытие оставшихся монстров и системное сообщение **57016** с именем лидера.
- Когда HP бойца становится 0, обработчик попадания переводит его модель в animation slot **6** (`kSlotDown`). Поэтому оба участника остаются лежать в кадре поражения. Это не команда EVT `Gosub 0xA1BF`: поза возникает ещё внутри боевой сцены.
- После выдержки сцены `Lost` идёт специальный выход группы 650 и возобновление сценария. Исправление должно сохранять весь интервал сообщения/позы и менять только дальнейший переход, не обрывая поражение сразу.

**Нативная iOS-последовательность после поражения:** в обработчике состояния боя переход из `0x4B1` (battle lose) расположен в районе **`0x12E14`**. Он:
- устанавливает story flag `0xFFD` через `0x20340`;
- включает музыку `0x1A`;
- переводит battle state в `0x513`;
- задаёт камеру `0x48` через `0x51064`;
- задаёт счётчики presentation `0x50` и `0x28` в полях `+0xAE8` / `+0xAEE`.

Это отдельная проигрышная фаза до дальнейшего выхода из боя. Она не эквивалентна мгновенному вызову Title. Следовательно, правильный порядок именно такой: **баннер «Виг и команда повержены» → лежащие модели/проигрышная выдержка → сюжетное продолжение**. Твоя наблюдаемая сцена совпадает с оригинальной экранной процедурой поражения.

**Сопоставление оригинала iOS:** в нативном battle-state manager есть отдельная классификация группы `0x28A` в `0x64D5C`; для этой группы сюжетная ветка не должна идти через общий сброс. Обработчик специальных сюжетных моментов `0x64E80` для `0x28A` поднимает `0xFFF`, используемый как gate выполнения сценарного EVT. Это согласуется с продолжением того же события после завершения боевой сцены, а не с переходом на Title.

**Ограничение доказательств:** точный денежный порог спасения Пиу-Пиу пока не подтверждён; сообщение 57016 и экранная процедура поражения подтверждены отдельно от этого порога.

## Что делает текущий порт

Проверенные участки `engine/src/main.cpp` на `main`:

- `stepEvents()`: EVT opcode 32 вызывает `EventHost::battle()`; VM возвращает управление на границе кадра, сохраняя PC после команды `Battle`.
- После этого `stepEvents()` вычисляет `event = more && app.runner.running()`, запускает бой и выставляет `app.battle.eventBattle = event && app.battle.active`. То есть признак событийного боя **сохраняется**; прежнее предположение, что он всегда теряется в `startBattle()`, неверно.
- `endBattle()` уже умеет возобновлять сохранённый EVT: снимает gate через `runner.setGate(-1)`; для `eventBattle == true` не останавливает runner и не ставит повторный Room Entry.
- Ошибка находится в обработке проигрыша: `stepBattle()`, `App::Battle::Lost`, после 120 кадров выставляет `exit = 2` для любого `eventBattle`.
- `drawFrame()` трактует `exit == 2` общим `else bootTitle(app)`. Поэтому сюжетный проигрыш группы 650 уничтожает нужное продолжение и отправляет игрока на титульный экран.

Обычное поражение обрабатывается иначе: `exit == 3` вызывает `loseToArk()`, которая возвращает героя в Ark и снимает 20% Oz. Этот путь нельзя сломать исправлением группы 650.

## Реализация в ветке

- В `stepBattle()`, для `Lost` после 120 кадров, добавлен отдельный исход **только** при `eventBattle && group == 0x28A`: `exit = 5`.
- В `drawFrame()` `exit == 5` вызывает `endBattle(app, false)` вместо `bootTitle()`.
- `endBattle()` снимает gate, очищает временный флаг боевых разговоров и оставляет уже приостановленный event runner активным; повторный Room Entry не ставится.
- Остальные сюжетные группы сохраняют прежний маршрут `exit == 2`, обычные бои — `exit == 3` и возврат в Ark. Исключение по группе используется здесь потому, что отдельная ветка группы 650 подтверждена оригинальным iOS-кодом; это не правило для моделей/анимаций.

## Регрессионный self-test, добавленный в ветке

В секции `battle talks` (`--selftest`) добавлен сценарий:

1. Загрузить область 9 / `j001_t01.evt`, событие 202.
2. Дождаться запуска `Battle 650` и проверить `eventBattle` и активный runner.
3. Смоделировать штатное состояние `Lost` и дождаться timeout.
4. Проверить `exit == 5`, закрытие боя, активный runner, снятый gate, отсутствие Title и Room Entry.
5. Выполнить следующий шаг EVT с трассировкой адресов и проверить, что трасса достигает `0xA1BF`.

**Статус проверки:** в пользовательском запуске подтверждены баннер 57016 и лежащие модели; их соответствие оригиналу подтверждено по `sys.evt` и iOS state manager. Добавленный self-test отдельно проверяет маршрут после поражения и продолжение EVT, но ещё не воспроизводит экранную фазу поражения. GitHub Actions run **#24** (`42211858930`) выполняется на актуальном head; запуск `--selftest` с оригинальными Omega data остаётся отдельной проверкой.

## Оставшиеся проверки перед слиянием

1. Проверить победу в группе 650: исправление не должно менять победный путь.
2. Проверить обычное поражение случайной встречи: возврат в Ark и текущая потеря 20% Oz остаются прежними.
3. Отдельно восстановить по оригинальному iOS-коду денежную проверку и rescue-путь Пиу-Пиу: точный порог Oz и поведение при недостатке денег пока не подтверждены этой правкой.
4. Проверить проигрыш других сюжетных боёв; не переносить правило группы 650 на все `eventBattle`.
5. Повторить сценарий на Vita после получения расшифрованного/доступного к анализу кода Vita; текущий `eboot.bin` — зашифрованный SELF.
