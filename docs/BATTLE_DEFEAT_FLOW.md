# Сюжетное поражение: первый бой Omega (группа 650)

**Дата:** 2026-11-06  
**Ветка:** `fix/scripted-battle-loss-resumes-event`  
**Статус:** оригинальная iOS-цепочка локализована; исправление runtime и регрессионный тест ещё не внесены.

## Цель

Первый сюжетный бой должен завершиться поражением героя и продолжением сюжетного сценария. Реконструкция вместо этого выводит игрока на титульный экран. Поведение нужно переносить из оригинального кода Omega, а не выводить из названий ресурсов или из текущего поведения порта.

## Источники и границы доказательств

| Источник | Что подтверждает | Статус |
|---|---|---|
| Оригинальный iOS `ChaosRingsOmegaHDeng`, Mach-O ARMv7 из пользовательского `ChaosRingsOmega.zip` | Нативный обработчик EVT `Battle`, обработка группы 650 и установка сюжетного gate-флага | Код незашифрован: `cryptid=0`; основной источник анализа |
| `j001_t01.evt` из того же архива | Сценарий 202 вызывает `Battle(650, 0)`, затем `Gosub 0xA1BF` | Проверено по оригинальному EVT |
| `eboot.bin` из того же архива | Это Vita SELF | Сегменты помечены зашифрованными; Vita-код пока не подтверждён дизассемблированием |
| `CRO-U-metastigma/engine/src/main.cpp` | Текущий переход порта после `Battle::Lost` | Проверено по исходнику ветки `main` |

**Ограничение:** совпадение поведения iOS и Vita пока не заявляется. Наличие Vita `eboot.bin` само по себе не доказывает, что Vita использует тот же путь.

## Оригинальная сценарная последовательность

В `j001_t01.evt`, событие **202**:

| Смещение в EVT | Команда | Значение |
|---:|---|---|
| `0xA124` | `Battle` | группа `650` (`0x28A`), stage `0`, flags `0` |
| `0xA129` | `Gosub` | продолжение по адресу `0xA1BF` |

После возврата из боя скрипт не должен заменяться новым комнатным entry-скриптом или титульным экраном: исполняться должна следующая команда уже приостановленного EVT. В `Gosub 0xA1BF` находится сцена с Вигом, Олгаром и Агентом; среди реплик — «Олгар?!», «Думал, я позволю тебе сделать это в одиночку?» и «Дураки. Вы — двое».

## Оригинальная iOS-реализация

1. Нативный обработчик EVT `Battle` находится по адресу **`0x22C8C`**. Он читает из байткода группу, stage и flags, помещает параметры в глобальный контекст боя и запрашивает переход в боевой режим.
2. В нативной процедуре обработки завершения боя **`0x64D5C`** обнаружена отдельная проверка группы **`0x28A` (650)**.
3. Связанная ветка в **`0x64E80`** устанавливает флаг события **`0xFFF`** через функцию установки флага **`0x20340`**. Это специальный сюжетный переход для группы 650; его нельзя заменять общей реакцией на поражение.
4. В этой же системе `0xFFF` используется как gate для исполнения событийного скрипта во время боя. Не следует называть его отдельным «флагом спасения Пиу-Пиу»: доказано его участие в управлении сюжетным EVT, а не полная семантика всех последующих проверок.

**Важно:** сейчас задокументирован нативный специальный путь группы 650 и сценарное продолжение. Точная ветка оплаты Пиу-Пиу, порог Oz и все исходы при недостатке денег требуют отдельной трассировки оригинальных проверок; они не должны подменяться догадкой.

## Что делает текущий порт

Проверенные участки `engine/src/main.cpp` на `main`:

- `stepEvents()`: EVT opcode 32 вызывает `EventHost::battle()`; VM возвращает управление на границе кадра, сохраняя PC после команды `Battle`.
- После этого `stepEvents()` вычисляет `event = more && app.runner.running()`, запускает бой и выставляет `app.battle.eventBattle = event && app.battle.active`. То есть признак событийного боя **сохраняется**; прежнее предположение, что он всегда теряется в `startBattle()`, неверно.
- `endBattle()` уже умеет возобновлять сохранённый EVT: снимает gate через `runner.setGate(-1)`; для `eventBattle == true` не останавливает runner и не ставит повторный Room Entry.
- Ошибка находится в обработке проигрыша: `stepBattle()`, `App::Battle::Lost`, после 120 кадров выставляет `exit = 2` для любого `eventBattle`.
- `drawFrame()` трактует `exit == 2` общим `else bootTitle(app)`. Поэтому сюжетный проигрыш группы 650 уничтожает нужное продолжение и отправляет игрока на титульный экран.

Обычное поражение обрабатывается иначе: `exit == 3` вызывает `loseToArk()`, которая возвращает героя в Ark и снимает 20% Oz. Этот путь нельзя сломать исправлением группы 650.

## Требуемое исправление

- Выделить для группы 650 подтверждённый оригиналом исход «поражение → возврат к текущему EVT».
- При этом исходе завершить battle runtime через штатный `endBattle(app, false)`, сохранив приостановленный runner и продолжив его со следующего байта после `Battle`.
- Не вызывать `bootTitle()`, `loseToArk()` или Room Entry для этого исхода.
- Оставить обычное поражение с возвратом в Ark и потерей Oz без изменений.
- Не распространять специальное правило на остальные группы сюжетных боёв без подтверждения оригинальным кодом.

## Регрессионные проверки перед PR

1. Запустить оригинальный сценарий 202 на карте/области, соответствующей `j001_t01.evt`, дойти до `Battle 650`.
2. Принудительно смоделировать поражение стороны героя, не меняя сценарные флаги до штатного исхода.
3. Убедиться, что бой закрывается, runner остаётся активным, его PC находится после `Battle`, выполняется `Gosub 0xA1BF`, игра остаётся в режиме поля и не открывает Title.
4. Отдельно проверить победу в группе 650: не направлять её искусственно в ветку поражения.
5. Проверить обычное поражение случайной встречи: переход в Ark и потеря 20% Oz должны остаться прежними.
6. Проверить проигрыш другого сюжетного боя, чтобы не изменить непроверенную нативную семантику остальных групп.
